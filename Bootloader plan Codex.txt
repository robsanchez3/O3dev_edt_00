• Análisis para boolaoder de Codex 

  El proyecto ya tiene casi toda la base para un bootloader por pendrive USB:

  - La app actual monta USB Host MSC y hace f_mount() cuando el dispositivo queda listo, así que la detección de USB flash ya existe en el código de aplicación: USB_Host/App/usb_host.c:50, USB_Host/App/
    usb_host.c:119.
  - Ese USB hoy depende de una tarea FreeRTOS, no de un arranque temprano: Core/Src/app_freertos.c:178, Core/Src/app_freertos.c:215.
  - La aplicación está enlazada desde 0x08000000 y el linker reserva toda la flash interna visible del proyecto, 2048K: gcc/STM32U599NJHXQ_FLASH.ld:45.
  - El VTOR también apunta a FLASH_BASE + 0, así que hoy no hay desplazamiento de vector table para una app detrás de bootloader: Core/Src/system_stm32u5xx.c:138, Core/Src/system_stm32u5xx.c:221.
  - El micro configurado en CubeMX es STM32U599NIH6Q: O3dev_edt_00.ioc:59.
  - La build genera por separado intflash.hex y extflash.bin, luego la “reprogramación total” no debería limitarse a la flash interna; también puede afectar contenido OSPI/TouchGFX: gcc/Makefile:391.

  Conclusión: es viable, pero no conviene meterlo dentro de la app actual. Lo correcto es un proyecto bootloader independiente, mínimo, sin RTOS ni TouchGFX, que arranque antes de la aplicación.

  Plan Propuesto

  1. Definir el alcance exacto de “reprogramación total”.
      - Mínimo: actualizar firmware interno.
      - Completo: actualizar firmware interno + extflash.bin en OSPI.
  2. Reservar espacio fijo para bootloader en flash interna.
      - Propuesta inicial: 128 KB o 192 KB en 0x08000000.
      - La app pasaría a arrancar en 0x08020000 o similar.
  3. Crear un proyecto nuevo Bootloader.
      - Sin FreeRTOS.
      - Sin TouchGFX.
      - Con init mínimo de reloj, GPIO, CRC, USB OTG HS Host MSC, FatFS y flash programming.
  4. Definir el flujo de arranque.
      - Reset.
      - Bootloader espera USB durante una ventana corta, por ejemplo 2-3 s.
      - Si encuentra un paquete válido de actualización, programa.
      - Si no, valida la app y salta a ella.
      - Si la app no es válida, queda en modo recuperación esperando USB.
  5. Definir un formato de paquete robusto.
      - Mejor un manifest + binarios, no un único .bin suelto.
      - Ejemplo:
          - update.json o cabecera binaria con magic, versión, tamaños, CRC/SHA.
          - app.bin
          - extflash.bin opcional
      - El bootloader nunca debe programar nada sin validar integridad completa.
  6. Adaptar la aplicación actual.
      - Cambiar linker para moverla detrás del bootloader.
      - Cambiar VTOR para que apunte a la nueva base de la app.
      - Añadir API “entrar en bootloader” desde menú de servicio:
          - escribir flag persistente
          - NVIC_SystemReset()
      - Parar SysTick/periféricos usados por bootloader.
      - Cargar MSP desde base de app.
      - Poner SCB->VTOR = APP_BASE.
      - Saltar al Reset_Handler.
  8. Programación segura de memoria.
      - Si solo se actualiza app interna: borrar/programar región app.
      - Si también se actualiza OSPI: programar extflash.bin después o antes según dependencias.
      - Verificar por CRC al final de cada región.
  9. Añadir mecanismo anti-brick.
      - Recomendado: staging area.
      - Si no hay segundo banco interno disponible en la configuración final, usar OSPI como staging temporal del nuevo app.bin.
      - No borrar la app válida hasta tener imagen nueva validada.
  10. Integrar generación de artefactos.

  - Aprovechar que ya existe intflash.hex/extflash.bin.
  - Añadir post-build que genere paquete de actualización consumible por bootloader.

  Decisiones Técnicas Recomendadas

  - Bootloader separado de la app: sí, obligatorio en la práctica.
  - USB detectado en arranque: sí, pero en bootloader propio, no esperando a que suba FreeRTOS.
  - Staging: sí, muy recomendable.
  - Actualización de OSPI: sí, si quieres “reprogramación total” real.
  - UI en bootloader: no al inicio; mejor LEDs/UART/log simple. La pantalla puede venir después.

  Riesgos

  - El principal riesgo no es USB, es la partición de memoria y el proceso de recuperación si falla una actualización.
  - Si se sobrescribe la app sin staging y sin validación previa, puedes dejar el equipo sin arranque funcional.
  - Si extflash.bin cambia y no se actualiza junto con la app, puedes tener incompatibilidades en assets/recursos.

  Fases de ejecución

  1. Confirmar mapa final de memoria disponible para bootloader, app y staging.
  2. Crear bootloader mínimo que detecte USB y lea paquete.
  3. Mover la app a nueva dirección y validar salto.
  4. Añadir programación de flash interna.
  5. Añadir actualización de OSPI.
  6. Añadir trigger desde aplicación y pruebas de recuperación.

  Paquete USB

  En el pendrive propondría una estructura simple y estable:

  /UPDATE/
    manifest.bin
    app.bin
    extflash.bin   <- opcional

  manifest.bin:

  typedef struct
  {
      uint32_t magic;          // 'O3UP'
      uint32_t format_version; // 1
      uint32_t app_size;
      uint32_t app_crc32;
      uint32_t ext_size;       // 0 si no hay update OSPI
      uint32_t ext_crc32;
      uint32_t target_addr;    // 0x08020000
      uint32_t flags;          // bit0=update app, bit1=update extflash
      uint32_t header_crc32;

  Secuencia de arranque

  1. Reset entra siempre en bootloader.
  2. El bootloader inicializa mínimo:
      - HAL_Init
      - clocks
      - GPIO
      - CRC
      - USB OTG HS Host
      - FATFS
  3. Espera 2-3 s a que aparezca USB MSC.
  4. Si no hay USB o no existe /UPDATE/manifest.bin, valida app y salta.
  5. Si hay paquete:
      - valida manifest
      - valida tamaños/direcciones
      - copia app.bin a staging en OSPI
      - verifica CRC
      - programa flash interna de aplicación
      - verifica CRC final leído desde flash
      - si existe extflash.bin, programa OSPI final y verifica
      - marca update OK
      - reinicia
  6. En siguiente arranque, si la app es válida, salta.

  Validación de aplicación

  Antes de saltar a la app, comprobar:

  - MSP inicial en rango RAM válido
  - Reset vector dentro del rango de aplicación
  - CRC opcional de la región app

  Salto a la app

  La app actual arranca con VTOR a FLASH_BASE: Core/Src/system_stm32u5xx.c:221

  Habrá que dejarla así:

  - APP_BASE = 0x08020000
  - SCB->VTOR = APP_BASE

  Y en el bootloader, el salto debe hacer:

  __disable_irq();
  SysTick->CTRL = 0;
  SysTick->LOAD = 0;
  SysTick->VAL  = 0;

  HAL_RCC_DeInit();
  HAL_DeInit();

  SCB->VTOR = APP_BASE;
  __set_MSP(*(uint32_t *)APP_BASE);

  void (*app_reset_handler)(void) = (void (*)(void))(*(uint32_t *)(APP_BASE + 4));
  app_reset_handler();

  Flujo exacto de boot

  1. Reset
  2. Bootloader lee flag de request
  3. Espera USB 2500 ms
  4. Si hay /UPDATE/manifest.bin, intenta actualización
  5. Si no hay update:
      - valida app en 0x08020000
      - salta a app
  6. Si app inválida:
      - entra en modo recuperación indefinido esperando USB

  Secuencia de actualización

  1. Montar USB MSC
  2. Leer manifest.bin
  3. Validar:
      - magic
      - format_version
      - app_target_addr == 0x08020000
      - tamaños dentro de rango
      - header_crc32
  4. Copiar app.bin a staging OSPI
  5. Verificar CRC staging
  6. Borrar flash interna de aplicación
  7. Programar app desde staging a flash interna
  8. Verificar CRC final sobre flash interna
  9. Si extflash.bin existe:
      - programar zona OSPI final
      - verificar CRC
  10. Limpiar flag y reset
